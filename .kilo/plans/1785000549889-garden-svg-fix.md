# 1785000549889-garden-svg-fix.md

## Problema
- `<circle attribute r: Expected length, "undefined">` (6 veces)
- `<line attribute y1/y2: Expected length, "undefined">` (docenas de veces)

El SVG del jardín (`GardenSvg.tsx` y `levels/module.tsx`) usa valores dinámicos que Framer Motion recibe como `undefined` durante animaciones o renders iniciales.

## Causa raíz
1. **Radio dinámico de partículas** (`0.7 + particle.scale * 0.8`). Si `particle` o `particle.scale` son `undefined` por cualquier razón, el resultado es `NaN` o `undefined`, lo que Firefox/Chrome convierte en el string `"undefined"` para el atributo SVG.
2. **Animación de `<motion.line>` en lluvia**. El `animate={{ y1: [-20, 480], y2: [440, 920] }}` no especifica valor inicial. Framer Motion puede enviar `undefined` en el frame inicial al montar el componente cuando `showRain` pasa de `false` a `true`.

## Cambios requeridos

### 1. `src/garden/GardenSvg.tsx` línea 186
Cambiar el `r` dinámico por un valor seguro con fallback:
```tsx
r={Math.max(0.1, 0.7 + (particle.scale ?? 0) * 0.8)}
```

### 2. `src/garden/levels/module.tsx` línea 234
Mismo fix defensivo:
```tsx
r={Math.max(0.1, 0.7 + (p.scale ?? 0) * 0.8)}
```

### 3. `src/garden/GardenSvg.tsx` línea 197-207 (lluvia)
Agregar `initial={{ y1: 0, y2: 460 }}` al `<motion.line>` para que Framer Motion siempre tenga un valor numérico de partida:
```tsx
<line
  x1={40 + i * 24}
  y1={0}
  x2={34 + i * 24}
  y2={460}
  initial={{ y1: 0, y2: 460 }}
  animate={{ y1: [-20, 480], y2: [440, 920] }}
  ...
/>
```

### 4. Asegurar valores numéricos en lights de `levels/module.tsx` (línea 196-197)
Aunque `makePoints` siempre produce números, agregar fallback defensivo:
```tsx
cx={l.x ?? 0}
cy={l.y ?? 0}
```

- Regar el jardín y confirmar que la animación de lluvia fluye sin errores.
- Verificar que niveles superiores rendericen partículas/luces extra sin crash.
